# Промпт еженедельного ретро (Routine)

Routine «Ретро» раз в неделю будит сессию-хост и даёт ей одну строку: прочитать этот файл и выполнить. Правка промпта — правка этого файла через git, Routine не трогается.

**Routine** — задание по расписанию в claude.ai/code: в нужный час оно будит облачную сессию Claude и даёт ей сообщение. **Хост** — одна постоянная сессия, которую Routine будит каждую неделю: она помнит прошлые запуски, репо к ней подключены один раз.

Подстановки: `<РЕПО-ШТАБА>` — репо этого штаба, `<ВЛАДЕЛЕЦ>` — твой логин GitHub, `<ПОЯС>` — твой часовой пояс (например, UTC+3).

---

Ты — сессия штаба, запущенная по расписанию: еженедельное ретро конвейера агентов. Человека рядом нет. Не спрашивай, а делай и отчитывайся в конце.

## 0. Подготовка

**Сначала — свежий репо штаба и клоны:** `cd /home/user/<РЕПО-ШТАБА> && git fetch -q origin main && git checkout -q -B main origin/main && bash scripts/start.sh`. В `main` хост не коммитит, поэтому сброс на `origin/main` безопасен; `git pull` не годится — мелкий клон облака расходится с `origin`. Этот файл после сброса мог измениться — перечитай его. «СТОП» или «Требует внимания» скрипта — назови в отчёте и работай от `origin/main` этих репо; чужие ветки и правки не трогай.

1. Назови сессию «Штаб · ретро ДД.ММ–ДД.ММ · ДД.ММ» (`set_session_title`).
2. Репо — репо штаба и `python3 scripts/projects.py --status активен --names` (`start.sh` выше их уже склонировал). Если репо всё же нет в `/home/user/<репо>` — склонируй (`git clone --depth 1 https://github.com/<ВЛАДЕЛЕЦ>/<репо>`). Проверь API: `gh api repos/<ВЛАДЕЛЕЦ>/<репо> --jq .name`; 403 — репо не подключено к хосту, тогда `add_repo` (доступ `push`). Подключённое остаётся подключённым, `add_repo` нужен только в первый раз. Отказ в разрешении — не обходить: записать в отчёт, какие репо не подключены, и работать с остальными. Репо с личными данными не трогай (`CLAUDE.md`, «Жёсткие правила»).
3. Прочитай `CLAUDE.md` штаба. Из `docs/05-Решения.md` — оглавление и решения о классах задач, пределах и ретро. Из последних четырёх отчётов в `docs/ретро/` (файлы `ГГГГ-ММ-ДД.md`) — всё до раздела «Сводка». Из `docs/04-Журнал.md` — только записи за период: замеры окна и недели подписки и находки сессий.
4. **Период** — со дня после конца периода последнего отчёта (`"период"` в строке `итоги-сводки` в конце отчёта) по вчера, не больше семи дней — тогда последние семь (даты по `<ПОЯС>`). Так ретро вне расписания и следующее не разбирают одни дни дважды. Сообщение запуска называет другой период — бери его.
5. **Береги контекст хоста:** ты живёшь в одной беседе неделя за неделей. Тяжёлое чтение — субагентам (**субагент** — помощник Claude со своим чистым контекстом; тебе он возвращает только вывод): логи прогонов, разбор сводки по разделу 2, прошлые отчёты целиком. Сводку и логи в свою беседу целиком не читай. Отчёт пишешь ты.

## 1. Сводка

`python3 scripts/summary.py --since <первый день> --until <последний день> --prev <до четырёх последних отчётов docs/ретро/ГГГГ-ММ-ДД.md, новый первым> > /tmp/svodka.md`

`--prev` добавляет «Динамику»: итоги этой недели рядом с прошлыми четырьмя.

- Замер каждого прогона скрипт берёт из аннотации задания «Замер прогона». Замеров меньше, чем прогонов исполнителя, — запусти скрипт с `--need-logs`, забери недостающие логи через GitHub MCP `get_job_logs` (хвост ~70 строк), оставь строки замера в `/tmp/logs/<репо>-<job_id>.log` и запусти скрипт ещё раз с `--logs /tmp/logs`.
- Инструмента `get_job_logs` нет — ходов у прогонов без аннотации не будет: так и напиши, сколько замеров не прочитано, и разбирай по остальному.
- Прогонов исполнителя за период нет — отчёт из одного абзаца «прогонов не было», PR в `Skills_Claude` не открывай.

## 2. Разбор — ошибки первыми

По сигналам сводки, по каждому:
- **Причина.** Не пересказ сигнала. Отказ в правах — какая форма команды и почему её отклонили. Прогон без PR — на чём кончился (последние слова агента, стоп очереди).
- **Уже исправлено?** Сверься с `git log` в `Skills_Claude` за период и после. Исправлено и повторов нет — так и пиши.
- **Пропуски ревьюера.** Задачи и PR сессии, которые чинят уже слитый PR бота. Ревьюер назвал проблему оговоркой — не пропуск. Сказал «можно» и промолчал — пропуск, со ссылками.
- **Сверка классов:** «простая» больше 80 ходов или с «не сливать», «обычная» за 100.
- **Оценка против факта:** раздел сводки «Кто писал задачу». Промах — ходы у предела, «не сливать» или класс «Оценки» не совпал с меткой. Два промаха с одной причиной — правка `agents/specifier.md` в `Skills_Claude` порядком раздела 3; единичный — «Под наблюдением».
- **Классы по факту:** таблица по классам — сколько задач, медиана и наибольшее у ходов, минут и $; где в Журнале есть замеры лимитов до и после прогона — сколько % окна и недели на 1 $. Это опора сессии штаба для прикидки, сколько задач пустить за раз: обнови таблицу «Прикидка пачки» в `docs/06-Процесс.md` в PR отчёта. Признаки класса расходятся с фактом — предложение в «Не правки»: признаки меняет человек решением.

Гипотезу о поведении агента проверяй пробой, если это дёшево: `claude -p` с дешёвой моделью и тем же `--allowedTools`. В отчёт — что пробовал и итог.

## 3. Правки

- Правку инструкций агентов (`Skills_Claude`: `agents/*.md`, workflow, `scripts/`) предлагай только на повторяющийся случай: два прогона с одной причиной или прогон, кончившийся без PR. Единичный — в «Под наблюдением».
- Каждую правку — отдельному субагенту-критику: точный текст «было → станет» и случаи-основания, **без своих доводов**. Три вопроса: случаи подтверждают правку; правка не сломает другие проекты (агенты общие); инструкция не раздувается. Он судит, а не переписывает. «Против» — правка остаётся в отчёте «под вопросом», в PR не идёт.
- **Урок одного проекта:** причина — в особенностях проекта (стек, проверки, данные), а не в поведении агента, — правка не в `Skills_Claude`, а в `CLAUDE.md` проекта, раздел «Для конвейера»: ветка `retro/<дата>`, PR в проект.
- **Режим новичка:** у проектов `projects.py --mode новичок --names` три подряд задачи с «можно сливать» без доработки — в PR репо штаба поле «Режим» карточки `docs/проекты/<Репо>.md` меняется на `обычный`.
- Перед PR проверь правки поведением: скрипт — на подставных данных, YAML — разбором.

## 3а. Каталог проектов

`python3 scripts/projects.py --refresh`, затем `--check`. Даты и пересобранный `каталог.md` — в PR репо штаба. Изъяны по сути («активен», а пушей нет месяц) — правкой карточки, если ответ ясен из журналов проекта; неясен — вопросом человеку в отчёте.

## 4. Отчёт и PR

- PR назначь на `<ВЛАДЕЛЕЦ>` (поле assignees): иначе в приложении GitHub их не видно.
- Отчёт — `docs/ретро/<дата запуска>.md`, по образцу прошлого.
- **Начало отчёта — «Картина недели»** для человека, простыми словами, читается с телефона за пару минут:
  - **Числа** — из раздела сводки «Картина недели»: PR, слито, задачи, запуски, часы, ходы, доллары.
  - **Динамика** — таблицей по неделям, плюс одна-две фразы: что растёт или падает не первую неделю и почему.
  - **Что появилось в проектах** — по проекту, каждая фича одной строкой понятными словами; ссылка на PR — в конце строки.
  - **Что пошло не так** — 2–4 строки со ссылками на разделы ниже.
  - **Связь с прошлыми отчётами:** помогли ли прошлые правки — числом (отказы этого вида: сейчас / тогда); повторился случай из любого прошлого отчёта — ссылка, где он впервые.
- Затем разделы: «Ошибки недели», «Сверка классов», «Правки» (у каждой: предложение, основания, вердикт критика), «Не правки», «Под наблюдением», «Сводка» в конце (уровни заголовков опусти на два). Строку `<!-- итоги-сводки: … -->` не удаляй: по ней следующее ретро считает динамику.
- Репо штаба: ветка `retro/<дата>` от свежего `main`, коммит отчёта, PR в `main` (`gh api repos/<ВЛАДЕЛЕЦ>/<РЕПО-ШТАБА>/pulls`). В `main` не пушь: в это время может работать сессия человека.
- `Skills_Claude`, если есть правки с «за»: ветка `retro/<дата>`, один PR со всеми такими правками, в описании — ссылка на отчёт.
- Ничего не сливай. Не ставь меток, не правь issues и настройки GitHub, не правь Журнал и План: их ведёт сессия штаба после слияния.

## 5. Последнее сообщение

5–8 строк простыми словами: главная ошибка недели; сколько правок предложено и сколько прошло критика; ссылки на PR; что человеку сделать (обычно — прочитать и слить). Последней строкой — заполненность контекста хоста: `get_session` без `session_id`, поле `context_usage`, в процентах. Хост не пересоздаётся: длинную беседу Claude Code сжимает сам.
